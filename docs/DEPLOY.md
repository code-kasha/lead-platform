# Deployment (free demo hosting)

One Docker image serves the whole app: the Django API, the Django admin, and the
built React frontend (same origin, so no CORS setup). It runs on **Render's free
web service**, with the database on **Neon's free Postgres**. Neither needs a
credit card, and neither expires, so the demo can stay up for months.

| Piece | Where | Free-tier limits that matter |
| --- | --- | --- |
| App (Docker) | [Render](https://render.com/docs/free) web service | Sleeps after 15 min without traffic; the next visit takes about a minute to wake it. 750 instance-hours/month, enough for one service running all month. |
| Database | [Neon](https://neon.com/docs/introduction/plans) Postgres | 0.5 GB storage, 100 compute-hours/month. Scales to zero when idle and wakes in about a second. |

Render also offers free Postgres, but it is **deleted 30 days after creation**,
which is why the database lives on Neon.

---

## 1. Create the database (Neon)

1. Sign up at [neon.com](https://neon.com) (GitHub login works; no card).
2. Create a project: pick **Postgres 17** and the region closest to your users.
   The blueprint puts the app in **Singapore**, so choose *AWS Asia Pacific
   (Singapore)* to keep the two close.
3. Open **Connect**, turn **Connection pooling off**, and copy the connection
   string. It looks like:

   ```
   postgresql://USER:PASSWORD@ep-xxxx.ap-southeast-1.aws.neon.tech/neondb?sslmode=require
   ```

   Use the direct (non-pooled) string: Django keeps its own connections open
   and doesn't work well behind the pooler's transaction mode.

## 2. Deploy the app (Render)

1. Sign up at [render.com](https://render.com) with GitHub (no card) and give
   Render access to this repository.
2. **New → Blueprint**, select the repository. Render reads `render.yaml` and
   asks for the values marked `sync: false`:

   | Variable | Value |
   | --- | --- |
   | `DATABASE_URL` | The Neon connection string from step 1 |
   | `DJANGO_SUPERUSER_EMAIL` | The email you'll log in with |
   | `DJANGO_SUPERUSER_PASSWORD` | A strong password (it is not length-checked, so choose a long one) |

   `SECRET_KEY` is generated by Render. The host and origin settings default to
   the service's `*.onrender.com` address.
3. Click **Apply**. The first build takes a few minutes. On start the container
   runs migrations, creates the admin account once, then starts the server.
4. Open the service URL (shown at the top of the service page) and log in.

## 3. After the first deploy

- **Team members**: log in at `/admin/` with the admin account and add users.
  New users get the *Member* role; set *Admin* where needed. There is no
  self sign-up.
- **Changing the admin password**: do it in `/admin/`. Restarts never reset it;
  `DJANGO_SUPERUSER_*` is only used to create the account the first time.
- **Updates**: every push to `main` redeploys automatically. Branch protection
  only lets CI-passing PRs merge into `main`.
- **Logs**: Render's *Logs* tab shows requests and any errors with tracebacks
  (`LOG_LEVEL` controls verbosity, default `INFO`).

## Ending the demo

Delete the service in Render and the project in Neon. Nothing is billed and no
card is on file, so there is nothing else to cancel.

## Running the production image locally

```bash
docker compose up --build   # then open http://localhost:8000
```

This builds the same image and runs it against a local Postgres, with demo
credentials from `docker-compose.yml` (admin: `admin@example.com` /
`admin-demo-password`). It serves plain HTTP, so HTTPS redirects and HSTS are
switched off there. The React app works fully; the Django admin login does not
work over plain HTTP, because its cookies are marked HTTPS-only.

## Environment variables

Required in production (startup fails with a message naming the missing one):

| Variable | Notes |
| --- | --- |
| `SECRET_KEY` | Long random value |
| `DATABASE_URL` | Postgres connection URL |
| `ALLOWED_HOSTS`, `CORS_ALLOWED_ORIGINS`, `CSRF_TRUSTED_ORIGINS` | Comma-separated. On Render they default to the service's own host; set them for a custom domain. |

Optional:

| Variable | Default | Notes |
| --- | --- | --- |
| `DJANGO_SUPERUSER_EMAIL` / `_PASSWORD` | unset | Creates the first admin once. `_FIRST_NAME` / `_LAST_NAME` are optional. |
| `LOG_LEVEL` | `INFO` | Console log level |
| `HSTS_SECONDS` | `3600` | See the README before raising it |
| `WEB_CONCURRENCY` | `2` | Gunicorn workers; 2 fits a 512 MB instance |
| `SECURE_SSL_REDIRECT` | `True` | Only turn off to try the image over plain HTTP |

## How the image is built

`Dockerfile` has two stages:

1. **Node**: installs the frontend with pnpm and builds it with
   `VITE_API_URL=/api`, since the API is served from the same origin.
2. **Python**: installs the backend, copies in the built frontend and
   pre-compresses it, runs `collectstatic`, and runs as a non-root user.
   `docker-entrypoint.sh` applies migrations, runs `ensure_superuser`, then
   starts gunicorn on `$PORT`.

Django serves `index.html` for every path outside `/api/`, `/admin/` and
`/static/`, so deep links like `/leads/7` survive a reload. WhiteNoise serves
the hashed files under `/assets/` gzipped, with a one-year immutable cache.
